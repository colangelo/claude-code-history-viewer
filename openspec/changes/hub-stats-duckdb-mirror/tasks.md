## 2. The mirror module

- [x] 2.1 Create `crates/hub/src/mirror.rs` owning the file and nothing else: `open_or_create`, `state() -> Warming | Ready { max_id, refreshed_at }`, `refresh() -> RefreshReport`. It MUST NOT know anything about statistics. *`rebuild()` is deliberately NOT here yet — it lands with 2.8, which owns the build-aside/atomic-swap behaviour*
- [x] 2.2 Define the mirror schema: the 13 `messages` columns the rollups read plus the derived `usage_row` and `conversational` booleans; `sessions` **including the provider session identifier**; `projects` **plus the project-identity tables** — every identifier a stats endpoint accepts (row id, session UUID, identity key) must resolve from the mirror alone, or the Postgres-outage scenario silently holds for only one endpoint; `message_tool_uses`; `message_tool_results`. Primary keys on mirrored row ids so inserts can be idempotent
- [x] 2.3 **DONE.** Explicit cold-build path: detected by an empty watermark, logged as a distinct phase with per-chunk progress against `max(id)` as a cheap denominator (a `count(*)` would not be), and reported with its elapsed time. Two things found while building it: (a) chunk inserts had to be wrapped in an explicit `BEGIN`/`COMMIT` — DuckDB autocommits per statement, so the cold build was paying one commit per row; (b) `RefreshReport` now carries `cold_build` and `elapsed`, because "is it progressing" is the only question anyone asks during the four-minute 503.
  **CORRECTION (2026-07-25, found during group 5): that first cut could not have completed a cold build of the real archive at all.** Wrapping the chunk in one transaction fixed the commit-per-row cost but left one `INSERT` *statement* per row, and DuckDB pins a 256 KiB block per statement until the transaction closes — **~370 KiB of memory per row**, measured: 676 rows exhausted a 256 MB limit and 2,753 rows exhausted the 1 GB default. It surfaced as `mirror_lifecycle_test` starting to fail *by growing test data* (the shared test DB crossed ~2.7k rows), not as a design review finding. At 2.8M rows the build would have died a few thousand rows in, every time, and a mirror that never finishes never serves — `/v1/stats/*` would have answered `503 warming` **forever** after the deploy, with the age header the health check watches never even starting. Fixed by batching 500 rows per statement through one `insert_all` helper that **all five** mirrored tables now share (each had its own copy of the per-row loop). Guarded by `crates/hub/tests/mirror_scale_test.rs`, which cold-builds 2,000 rows under a deliberately tight 256 MB limit — **verified non-vacuous**: with the batch size forced back to 1 it fails with exactly the original `Out of Memory Error: could not allocate block of size 256.0 KiB`. Rehearsed locally at **205,041 messages in 11.5 s inside the same 256 MB limit** (debug build, `CCHV_SCALE_ROWS=200000`), i.e. flat memory at 100x the old cliff
- [x] 2.4 Implement incremental refresh with the **overlap re-scan**: fetch rows from an overlap window behind the watermark (by id, or by ingest `created_at` over the last several minutes — ids are allocated at insert but commit out of order under concurrent ingest, so `WHERE id > max_id` alone skips rows forever), insert with `INSERT OR IGNORE`, and compute the derived booleans for genuinely new rows only (design D2)
- [x] 2.5 **DONE.** `AtomicBool` latch released by an RAII guard, so an early `?` or a panic cannot wedge every later tick; `refresh()` returns `RefreshOutcome::{Ran, Skipped}`. Tested by racing two refreshes (`mirror_lifecycle_test`)
- [x] 2.6 On an unopenable or corrupt mirror, move the file aside under a timestamped name and rebuild. Never delete
- [x] 2.7 **DONE — and verified non-vacuous:** re-running with `overlap_rows = 0` (i.e. the naive `WHERE id > max_id`) fails on exactly the late-commit assertion, so the test genuinely covers the bug rather than passing by construction. Unit-test D2 in all three shapes: a row that joins an existing dedup group is not usage-bearing; a row with an older timestamp under a newer id (the Time Machine backfill shape) leaves its group's totals unchanged; **a lower-id row becoming visible after higher ids were already mirrored is picked up by the overlap re-scan exactly once**
- [x] 2.8 **DONE.** `hub mirror rebuild` builds at `<path>.rebuild-<stamp>`, closes cleanly (checkpointing away the staging WAL) and `rename`s into place. Tested end to end: two rows, then a `message_id` UPDATE merging them, then the assertion that incremental refresh still reports 200 tokens (the bug) and the rebuild reports 100 (the fix). **One thing the task did not anticipate and the property needed:** a `rename` leaves the running hub's handle on the old inode, so it would have served pre-rebuild data until someone restarted it — precisely the data the rebuild exists to correct. `Mirror::adopt_replacement()` compares the file's inode each refresher tick and reopens, so the swap is picked up with no restart; it is idempotent, and it runs under the single-flight latch so no write can straddle the swap. Every refresh now ends with `CHECKPOINT` so a WAL never straddles one either. Runbook written in `docs/archive/deployment.md` § "`backfill-analytics` and `mirror rebuild` travel together"

## 4. Port the rollups

- [x] 4.1 **DONE** (`crates/hub/src/stats_duck.rs`). Scope is now a filter and a join over stored `usage_row` / `conversational`; measured at 0.066 s on the live archive against Postgres' ~3.4 s window function
- [x] 4.2 **DONE.** All eight, same signatures, same `history-core` types
- [x] 4.3 **DONE**, and verified by 4.5 rather than by inspection. Two incidental findings: `sum()` over `BIGINT` widens to `HUGEINT` in DuckDB and will not decode into an `i64`, so every token sum carries an explicit `::BIGINT`; and the top-N rollups had **no tie order at all** in the Postgres original, so which of several equally-used tools survived the cut varied between identical requests. Both implementations now tiebreak on name (`COLLATE "C"` on the Postgres side, to match DuckDB's byte ordering)
- [x] 4.4 **DONE.** Every stats handler reaches the mirror through one `stats_api::with_mirror` helper that takes a cloned connection onto `spawn_blocking` — so the hop is structural rather than remembered, and a new endpoint cannot skip it. **One blocking hop per request, not one per query**: the closure does reference resolution, identity expansion *and* the rollups inside it, and the cloned connection is what keeps that request's `stats_scope` TEMP table private to it
- [x] 4.5 **DONE — PASSED, twice, at two levels.**
  1. *SQL level, live data.* All eight rollups run against pg1 and against a DuckDB copy of the same rows, both pinned to `id <= 36101458` so neither saw the archive grow mid-run. **All 700 output rows byte-identical** — totals, ~450 daily rows, 168 heatmap cells, models, providers, top projects, every tool/skill/subagent row. Postgres **16.65 s**, DuckDB **0.535 s** (**31×**) over 2,818,119 messages. Per statement, DuckDB: scope 0.066 · totals 0.253 · daily 0.062 · heatmap 0.044 · providers 0.017 · top projects 0.020 · tools 0.020 · models 0.007.
  2. *Implementation level, in CI.* `crates/hub/tests/stats_differential_test.rs` runs both implementations over the same fixtures and requires their **serde representation** to be equal — so a field added later is compared without anyone remembering to. Three scopes (global, project, session) × four windows (unbounded and bounded, UTC and `Europe/Rome`, the bounded Rome case deliberately straddling a day boundary that moves with the zone). All pass.
  The one predicted divergence is asserted rather than left to be rediscovered: `boundary_straddling_group_is_the_documented_d3_divergence` builds a logical message spanning midnight and shows Postgres attributing its usage inside the window while the mirror attributes it to the global group minimum outside — and asserts the difference is **one-directional** (the mirror can under-attribute a straddling group, never double count it)
- [x] 4.6 **DONE — gate re-run green on this tree first** (`stats_differential_test`, 4 tests, immediately before the deletion), per the ordering rule. The Postgres rollups, `materialize_scope` and the differential test are gone; with one implementation left, `stats_duck.rs` **is** the statistics module, so it absorbed `Window`/`Scope` and took the `stats.rs` name — leaving a `stats.rs` that held two types next to a `stats_duck.rs` that held all the statistics would have been transitional debris. Two things were deliberately *kept* out of the deletion: `stats_test.rs`'s thirteen rollup-semantics tests (dedup, uuid fallback, cross-session groups, cost coverage, tz bucketing, windows, D10 success rate, skills/subagents, session scope, model/provider dedup) now run against the mirror with **every assertion unchanged** — only a mirror refresh was inserted, inside the helpers, so the bodies read as they did; and the D3 boundary divergence, re-expressed as a mirror-only test (`a_group_straddling_the_window_edge_attributes_usage_outside_it`) asserting both halves of the documented behaviour — under-attribution inside a straddling window, never a double count outside one.

It now selects files **by content** (any `src/*.rs` mentioning `duckdb`), so a new DuckDB module is covered automatically, and asserts that what it scanned actually contains the rollup SQL — a rename could otherwise have left it passing while checking nothing. Postgres-only modules stay excluded on purpose: `journal.rs` and `health.rs` use `AT TIME ZONE` legitimately
- [x] 4.7 **DONE.** `stats_api_test.rs` runs against a hub with a real mirror attached: same fixtures, same assertions, one added step (`ingest → refresh → assert`). **That the expectations did not have to change is the result** — the endpoints' contract is identical, only their data source moved. Two fixture repairs the mirror path forced, both latent isolation bugs rather than new problems: session ids are now run-unique (the test DB persists, so a fixed provider session id would exist on this run's machine *and* every earlier run's, turning a by-id lookup into an *ambiguous* one on the second run), and each test gets its own mirror file (a shared one would let one test's refresh decide another's readiness)

## 5. Endpoint surface

- [x] 5.1 **DONE.** All three endpoints read only from the mirror; a mirror that is missing *or* still warming answers `503` with `Retry-After: 30` and a body that says so. 30 s is a poll rate, not an ETA — the cold build takes minutes, and the point is that the webapp's Analytics tab recovers on its own rather than sitting on an error until someone reloads. **The project endpoint no longer touches Postgres either**: identity expansion runs against the mirrored `projects` + `project_identity_aliases` (`stats_duck::resolve_identity_paths`/`identity_display_name`), so the Postgres-outage property now genuinely holds for all three scopes instead of two
- [x] 5.2 **DONE.** Both headers on every `200`, read from the mirror state *before* the rollup runs so they describe the data the response was computed from rather than a refresh that landed mid-request. **They also had to be added to the router's CORS `expose_headers`** — per the Fetch spec a script cannot read a response header that is not exposed, and the webapp calls the hub cross-origin, so without that the headers would exist and be invisible to their only consumer (the same trap `X-Total-Count` hit). Asserted in `stats_api_test`, including that the stat *bodies* stayed unchanged
- [x] 5.3 **DONE.** `status` is one of `ok` · `stale` · `lagging` · `warming` · `unavailable` — `warming` (building) and `unavailable` (file unopenable) are distinguished because they need different operator responses. Threshold defaults to the mirror's configured `stale_after_secs`, overridable per request. **The lag budget is opt-in (`?max_lag_rows=N`) and absent by default**: under live ingest a healthy mirror always trails by whatever arrived since its last refresh, so any default would be a guess about ingest rate dressed up as a health rule — and like `healthz_ingest`'s `?exclude=`, keeping it a query param leaves the policy in the Gatus check where it can be tuned without a hub redeploy. A Postgres read failure reports `postgres_max_id: null` and does **not** flip the verdict: `/v1/healthz` already owns database reachability, and blaming the mirror for a Postgres outage is worse than saying nothing
- [x] 5.4 **DONE.** `Path<String>`, resolved by `stats_duck::resolve_session_ref` against the mirror. Two deliberate details: an **ambiguous** provider session id (the same session synced from two machines) is a `400` listing the candidates, matching browse — resolving it to the lowest id silently would report one machine's copy as if it were the whole session; and a **numeric** reference is *checked* against the mirror rather than trusted (browse trusts it), because the row is right there to check and the alternative is discovering the absence downstream as an empty rollup
- [x] 5.5 **DONE**, in `stats_api_test.rs`. Warming: `503` + `Retry-After` and no staleness headers, then `200` **in the same process** after one refresh. Headers: RFC3339 parseable, age within a minute, bodies unchanged, and CORS-exposed. Health in every state — warming, fresh (`lag_rows == 0`, `mirror_max_id == postgres_max_id`), stale (by backdating the recorded refresh time rather than sleeping, so it is exact and fast, plus a wider threshold to prove the verdict is the threshold's and not the backdating's), and lagging (un-mirrored rows show as lag but stay `200`; only `?max_lag_rows=0` turns it into a `503`, and a refresh clears it). #26's four cases plus a non-numeric non-UUID string, all `404`, and the ambiguous case as a `400`
